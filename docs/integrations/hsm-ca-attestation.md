# Planning HSM key attestation with an outside CA

This is an operator planning guide. No enrolment, purchase, CA upload or production use is authorised by these instructions. Justin must approve any real provider interaction first. Brigalow does not implement vendor attestation tooling and cannot establish public trust itself.

The [evidence register](../research/evidence-register.md), captured 2026-11-11, lists vendor statements rather than tested capabilities. Sectigo C4 documents particular HSM families; SSL.com L4 lists bring-your-own-HSM fees. Neither establishes acceptance of every model, firmware, mechanism, region or certificate programme. Confirm current requirements directly with the chosen CA after approval. SoftHSM2 proves software integration only; its attributes are not hardware attestation.

1. Select the intended certificate programme and relying platforms. Record the CA's exact accepted HSM model, firmware, key algorithm, attestation format, challenge/freshness requirements and identity-validation process. Record source dates and obtain written clarification for unknowns.
2. Establish separate HSM operator and Brigalow custodian roles. Use a dedicated non-exportable signing key generated inside the approved device. Preserve `CKA_SENSITIVE=true` and `CKA_EXTRACTABLE=false`; do not import or export a private key to satisfy an enrolment workflow.
3. Generate a public CSR through Brigalow's custodian route, and obtain the device's attestation using its vendor-supported tooling. Brigalow's PKCS#11 attributes and CSR proof-of-possession alone are not vendor attestation. Verify that the attested public key is exactly the CSR's public key. Follow the CA's challenge procedure without inventing an attestation format or cryptographic primitive.
4. Keep HSM PINs, administration credentials and attestation bootstrap material out of repositories, tickets and logs. Before any authorised submission, inspect the vendor package for public-key binding, device identifiers and unnecessary sensitive data. Retain public evidence and approval records under the operator's retention policy.
5. When an issued chain is available, import it through the custodian API. Brigalow checks key match, time, signing usage and chain validation. Configure an independently obtained anchor with `tier="external-ca"` and a descriptive name. The UI's label records operator configuration; the relying platform makes its own trust decision.
6. Require an explicit release policy, verified protected-ref claims and the intended approvers/gates. Exercise activation, window caps, timestamp verification, revocation and disable procedures in an approved test environment before any release. Independently verify the actual artifact format on every target platform.

If the CA rejects the device or attestation, stop. There is no software fallback or key-export workaround. Record the incompatibility and seek an approved alternative. For a remote CA-held key, use an independently reviewed integration meeting the provider's authentication requirements; the current CSC mock backend cannot contact that provider.

Incident handling must distinguish Brigalow disable (stops this control plane), HSM access revocation (stops device credentials) and CA certificate revocation (informs relying parties). None substitutes for the others. Retain audit checkpoints outside the signing host and test recovery without exporting private keys.
